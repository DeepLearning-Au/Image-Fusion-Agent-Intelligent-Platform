# 第四课：轻量 PDF 解析流水线

## 1. 这一步解决什么问题

旧方式主要从 PDF 中读取文字。遇到扫描件、产品参数表和设备外观图时，会出现四类问题：

- 扫描页没有可检索文字；
- 表格被打散为顺序混乱的文本；
- 产品图片没有被保存；
- 入库成功不等于解析正确，缺少逐页证据。

本次升级不是简单增加 OCR，而是把 PDF 解析拆成可观察、可替换的流水线。

## 2. 三个组件各自负责什么

### 2.1 PyMuPDF：普通 PDF 和图片

PyMuPDF 是默认入口。它先逐页读取 PDF 自带的文字，并提取满足尺寸条件的嵌入图片。电子版产品手册通常直接走这条通道，速度快，也能最大程度保留型号、数字和单位。

### 2.2 RapidOCR：只处理扫描页面

系统不会对整份 PDF 无条件 OCR。每页先计算有效字符数、乱码比例和质量分；只有原生文字不足或质量过低时，才渲染该页并调用 RapidOCR。

这样做的原因是：OCR 比原生提取更慢，而且可能把 `0/O`、`1/I`、乘号、温度符号和型号识别错。按页路由既节省资源，也降低错误率。

### 2.3 pdfplumber：基础表格

pdfplumber 从电子 PDF 中提取规则表格。系统同时生成：

- Markdown 表格：供 RAG 检索和大模型阅读；
- JSON 行列数据：供以后写入结构化产品参数库或人工审核。

表格块会尽量保持完整，不再按照普通段落粗暴切碎。

## 3. 为什么放进独立 Worker

PDF 解析依赖和主 Agent 分离在 `.venv-pdf-parser` 中，主程序通过子进程调用 Worker，并接收统一 JSON。

这样做有四个企业级收益：

1. **环境隔离**：OCR、ONNX 和 PDF 库不会污染主服务依赖。
2. **故障隔离**：解析单个异常 PDF 不会直接拖垮聊天与检索服务。
3. **超时控制**：主程序可以限制单次解析最长时间。
4. **可替换性**：以后换成 PaddleOCR、MinerU 或远程文档解析服务，只需替换适配层。

## 4. 一份 PDF 的实际处理流程

```text
PDF
  ↓
PyMuPDF 逐页提取原生文字
  ↓
页面质量检测
  ├─ 质量合格 → 使用原生文字
  └─ 质量不足 → 渲染页面 → RapidOCR
  ↓
pdfplumber 提取基础表格
  ↓
PyMuPDF 导出有效嵌入图片
  ↓
统一解析结果（正文 + 表格 + 图片资产 + 逐页报告）
  ↓
SQLite 文档/页面记录 → Chunk → RAG 检索
```

## 5. 数据库里新增了什么

文档级记录新增：

- 使用的解析器及版本；
- 总页数、原生解析页数、OCR 页数；
- 待复核页数和解析警告数；
- 表格总数和有效图片总数；
- 完整解析报告 JSON。

页面级记录新增：

- 当前页采用原生提取还是 OCR；
- 质量分、有效字符数和乱码比例；
- OCR 置信度；
- 表格数、图片数和资产地址；
- 需要人工处理时的明确原因。

这些字段让“知识入库”从一次黑盒操作变成可检查的生产流程。

## 6. 升级前后对比

| 能力 | 升级前 | 当前版本 |
|---|---|---|
| 电子 PDF 正文 | 基础文字读取 | PyMuPDF 逐页原生提取与质量评分 |
| 扫描 PDF | 无法可靠入库 | 仅低质量页面调用 RapidOCR |
| 参数表格 | 容易打散 | pdfplumber 提取并生成 Markdown/JSON |
| 产品图片 | 不自动处理 | 自动导出、去重并过滤大面积空白装饰图 |
| 可观测性 | 只知道是否入库 | 文档级和页面级解析报告 |
| 运行隔离 | 依赖混在主环境 | 独立轻量 Worker 和超时控制 |

当前 3 份真实产品手册的结果：6 页全部走原生文字通道，识别 4 个基础表格，提取 24 张有效嵌入图片（包含产品图和资料图），生成 29 个 Chunk。12 题检索基线保持 `Recall@5 91.67%`、`Top1 91.67%`、`MRR 91.67%`，关键词覆盖率保持 `72.22%`。

为了证明 OCR 通道不是“只写了代码没有运行”，还对一份手册执行了强制 OCR 验证：2 页均成功完成识别，平均页面置信度分别约为 `0.998` 和 `0.970`，关键型号与协议词可被识别。

## 7. 如何安装和观察

首次安装或重建独立环境：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup_pdf_parser_worker.ps1
```

如果系统没有把 Python 加入 `PATH`，可以显式指定启动 Python：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup_pdf_parser_worker.ps1 -BootstrapPython "D:\Python312\python.exe"
```

启动项目后打开知识库管理页：

1. 顶部状态卡确认“PDF解析器：可用”；
2. 点击“从 data/knowledge_docs 重建”；
3. 在文档列表查看原生解析、OCR、表格和图片数量；
4. 点击“解析报告”，逐页检查质量分、解析方式和警告。

## 8. 现在还没有解决什么

这不是复杂版面理解模型，因此当前不承诺：

- 把扫描表格精准还原成行列；
- 理解图片里是哪一种产品或自动生成可靠图注；
- 自动把 PDF 参数直接发布为可销售的结构化商品；
- 自动判断红外与可见光设备能否硬件同步、配准并送入 MambaDFuse。

下一步应增加“产品参数候选抽取 + 人工审核 + 发布版本”，把 PDF 中的表格数据安全地转入结构化产品数据库。
