# 第 1 课：业务契约与评测基线

## 本课目标

把旧的“光学—SAR”演示系统，收敛为“红外/可见光设备选型与 MambaDFuse 融合”系统，并建立后续每次升级都能复用的评测基线。

## 为什么先做这一步

Agent 不只是一个大模型调用工具的程序。它首先需要一个稳定的业务契约：服务谁、能回答什么、不能回答什么、什么时候必须查资料、什么时候必须拒绝推断。

如果业务定义仍然混乱，那么更换向量数据库、Embedding 或 LangGraph 只会让错误以更复杂的方式出现。企业开发因此通常遵循以下顺序：

1. 定义业务边界；
2. 建立可重复评测；
3. 改进实现；
4. 用同一评测证明改进有效。

## 本次业务契约

系统只覆盖三类产品：

- 纯红外设备；
- 纯可见光设备；
- 红外可见光双模态设备。

系统有三项主要能力：

- 基于公开产品资料回答参数问题；
- 根据用户需求推荐设备或设备组合；
- 对同一场景的红外图像和可见光图像执行 MambaDFuse 融合。

当前不把 SAR 雷达设备当作红外设备。遇到 SAR 问题时，系统应说明知识库未覆盖，不能混用概念。

## 为什么文档写了“双光融合”仍不能直接判定适合 MambaDFuse

厂家内置融合和我们的外部模型融合不是一回事。用于 MambaDFuse 至少还要确认：

- 能否分别取得红外和可见光图像；
- 两路图像是否拍摄同一场景；
- 是否有同步时间戳或硬件触发；
- 两个镜头视场是否能够标定和配准；
- 图像是否经过严重压缩；
- 是否提供 SDK/API 获取数据。

这也是后续产品数据库必须增加“融合适配字段”的原因。

## 评测集怎么设计

当前评测集包含 12 道题，覆盖：

- 红外设备分辨率、帧率、测温、镜头和 SDK；
- 可见光设备传感器、全局快门、像素格式、触发和帧率；
- 双模态设备分辨率、环境适应性、协议和融合适配性。

每道题保存：问题编号、业务意图、期望文档和必须覆盖的关键词。

## 四个基础指标

- `doc_hit_rate_at_k`：前 K 个结果中是否出现正确文档。
- `top1_accuracy`：第一名是否就是正确文档。
- `MRR`：正确文档出现得越靠前，分数越高。
- `keyword_coverage`：召回内容覆盖了多少关键事实。

旧评测只要“任意文档有结果”就算命中，容易得到虚假的高分。新评测必须命中预先指定的产品文档。

## 本轮暂时保留的兼容设计

后端和前端上传字段仍叫 `optical_file` 与 `sar_file`。这属于旧接口兼容层，本轮只修改用户看到的名称，不同时重写融合调用链。

下一次处理接口与数据模型时，会引入正式字段 `visible_file` 和 `infrared_file`，并在过渡期兼容旧字段。这样可以避免一次修改过多导致问题难以定位。

## 本课验收标准

- 知识库只包含当前三份正式产品文档；
- 旧 SAR 评测题被替换；
- 评测接口使用统一评测文件；
- 前端、主提示词和报告面向红外—可见光业务；
- 能输出四项可重复比较的检索指标。

## 2026-08-27 实际基线结果

知识库重建结果：

- 文档数：3；
- 分块数：11；
- FTS5：可用。

检索基线：

- `doc_hit_rate_at_k`：91.67%；
- `top1_accuracy`：91.67%；
- `MRR`：91.67%；
- `keyword_coverage`：72.22%。

失败样本是“双模态设备的红外和可见光分辨率分别是多少”。资料中明确存在答案，但当前 LIKE 与人工关键词检索没有召回文档。这说明文档内容没有问题，主要短板在查询理解和召回方式。该问题将保留为后续混合检索升级的固定回归样本。
