# 第三课：智能 PDF 解析器

## 1. 为什么不能直接对所有 PDF 做 OCR

PDF 有两种常见来源：

- 文字型 PDF：内部包含文字对象，可以直接提取，速度快、准确率高；
- 扫描型 PDF：页面本质上是图片，需要 OCR 才能得到文字。

如果对文字型 PDF 再做 OCR，会增加耗时，也可能把型号、单位和符号识别错。因此企业级方案首先要做的是“页面路由”，而不是“所有页面统一 OCR”。

## 2. 本次升级的解析决策

解析器逐页统计：

- 原始字符数；
- 有效中英文和数字字符数；
- 乱码比例；
- PDF 图片对象数量；
- 页面质量分。

当前规则：有效字符达到 80 且乱码比例不高于 2%，使用原生文字；否则把页面交给 OCR 接口。OCR 未配置时，页面会明确显示为 `needs_ocr`，而不是把空白内容或错误信息写入知识库。

## 3. 为什么保存逐页解析报告

没有报告时，“成功入库”可能只是数据库里多了一条记录，无法证明内容正确。逐页报告让我们可以回答：

- 哪几页通过原生文本解析；
- 哪几页调用了 OCR；
- 哪几页仍需人工检查；
- 每页提取了多少有效字符；
- 页面是否可能存在图片内容。

这属于知识库的可观测性，是后续表格识别、图片提取和人工审核的基础。

## 4. 当前实现

现在采用独立的轻量 PDF Worker：

- PyMuPDF 提取普通 PDF 的原生文字和嵌入图片；
- 逐页质量检测决定是否需要 OCR；
- RapidOCR 只处理文字不足或乱码过多的扫描页；
- pdfplumber 提取电子 PDF 中的基础表格，并同时保存 Markdown 与结构化行列数据；
- 主应用只接收统一 JSON 结果，因此以后替换某个解析组件不需要重写入库逻辑。

这套方案已经安装在项目专用的 `.venv-pdf-parser` 环境中，不会把 OCR 依赖塞进主 Agent 环境。

## 5. 如何观察效果

打开知识库管理页，在文档列表中可以看到：

- 解析器名称和版本；
- 解析状态；
- 总页数；
- 原生解析页数；
- OCR 页数；
- 待 OCR 页数。

点击“解析报告”可以查看每一页的解析方式、质量分、有效字符数、乱码比例和警告。

## 6. 本项目三份产品手册的实际结果

| 文档 | 页数 | 原生解析页 | OCR 页 | 待 OCR 页 | 每页有效字符 | 质量分 |
|---|---:|---:|---:|---:|---|---|
| GuideIR IPT640M | 2 | 2 | 0 | 0 | 382、647 | 1.0、1.0 |
| HIKROBOT MV-CA050-12UC | 2 | 2 | 0 | 0 | 879、718 | 1.0、1.0 |
| GuideIR MC-FT | 2 | 2 | 0 | 0 | 560、1021 | 1.0、1.0 |

轻量解析器共识别 4 个基础表格、提取 24 张有效嵌入图片（包含产品图和资料图）。表格作为完整语义块参与切分后，共生成 29 个 Chunk。原有 12 题 RAG 评测仍为：`Recall@5 = 91.67%`、`Top1 = 91.67%`、`MRR = 91.67%`，关键词覆盖率保持 `72.22%`。这说明本次升级增加了表格、图片和解析质量治理，同时没有破坏原有检索结果。

## 7. 当前能力边界

- pdfplumber 适合电子 PDF 中结构较规则的基础表格；扫描表格暂时只能通过 OCR 得到文字，不能保证恢复为正确行列。
- RapidOCR 负责文字识别，不负责理解产品图、参数含义或自动判断两个模态是否能配准。
- PyMuPDF 可以导出 PDF 内嵌图片，但图片语义标注、图片与型号绑定仍需后续治理。
- 图片、表格和正文已能进入统一解析报告，但发布前的人工审核与知识库版本切换属于下一阶段。
